## 0. この手順書の使い方

### 原則：下から順に潰す。飛ばさない。

いきなりパイプライン全体を動かそうとすると、失敗したときに原因の切り分けができなくなる。**STEP 1 → 2 → 3 → 4 → 5 の順に、各ステップの合格条件を満たしてから次へ進む。**

### 所要時間の目安

| STEP | 内容 | 目安 |
|---|---|---|
| 0 | 物理接続・ネットワーク設定 | 15分 |
| 1 | マイク受信確認 | 10分 |
| 2 | SSH可否の確認（ルート分岐） | 5分 |
| 3 | ブリッジ配置 or 縮退準備 | 15分 |
| 4 | スピーカー再生確認 | 10分 |
| 5 | パイプライン全体 | 15分 |
| 6 | 調整・計測 | 残り時間 |

**STEP 0〜4 で1時間**を見ておく。ここが通れば STEP 5 は事前に完成させてあるので設定切り替えだけで動く。

### G1は共有機材：環境を変えない

**この手順書はG1に一切変更を加えない前提で書いてある。**

- `pip install` しない（ブリッジは標準ライブラリだけで動く）
- `sudo` を使わない（設定ファイルもシステムサービスも触らない）
- Wi-Fiを有効化しない（有線のみで完結させる）
- 置くファイルは `/tmp` に限定（再起動で消える）
- 音量は起動時に記録し、終了時に自動で元へ戻す

もしどうしても変更が必要になった場合は、**機材の管理者に確認**し、何を変えたか記録して元に戻すこと。

### 撤退ラインを決めておく

各ステップに「ここまでやって駄目なら次の手に移る」時間を書いてある。**限られた実機時間を1箇所で溶かさないこと。** 特にSSH接続とSDKのビルドは沼になりやすい。

### 1.4 インターネット接続の確保

OpenAI APIを叩くのでインターネットが要る。ただし**G1との通信は有線（192.168.123.x）**を使うので、次のどちらかになる。

- PCの有線＝G1、Wi-Fi＝インターネット（推奨。同時に使える）
- スマホのUSBテザリング＋有線＝G1

Wi-Fiとの併用時、Windowsが有線側をデフォルトゲートウェイにしてしまうとインターネットに出られなくなる。G1側のNICには**デフォルトゲートウェイもDNSも設定しない**こと。設定・確認手順は 2.2.1 を参照。

### 1.5 USB-Ethernetアダプタの事前確認【重要】

PCに有線ポートが無くUSBアダプタで増設する場合、**ここが当日の単一障害点になる。** 前日に必ず通しておく。

#### 手順1: 認識されるか

アダプタを挿して確認する。

```powershell
Get-NetAdapter | Format-Table Name, InterfaceDescription, Status, LinkSpeed
```

新しいアダプタが出てこない、または「!」付きで出る場合はドライバが必要。チップセット（RTL8153 / RTL8156 / AX88179 など）を `InterfaceDescription` で確認し、メーカーのサイトから入手する。**当日ネットが不安定な場所でドライバを探す羽目になるのは避けたい。**

> **本命は BENFEI の単機能アダプタ**（USB 3.0 → RJ45 Gigabit）。ハブもビデオ出力も持たないので、電力面でも障害点の数でも一番素直な構成。この形状のアダプタは RTL8153 系か AX88179 系がほとんどで、どちらもWindowsが標準ドライバを持っていることが多い。実際のチップセットは `InterfaceDescription` に出るので、挿した時点で分かる。
>
> **予備のWAVLINKドックを使う場合**: 同社のドックは **RealTek RTL8153B** または **ASIX AX88179 / AX88179A** を採用している（メーカーFAQによる）。認識されない場合、WAVLINKのFAQは次の順で対処するよう案内している。
> 1. RealTek または ASIX のサイトからチップセット用ドライバを入れる
> 2. それでも駄目なら、レジストリの `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\Network` 配下から `PID_8153` を含むキーを削除して再起動
>
> **手順2は前日の作業。当日ぶっつけでレジストリを触るのは避ける。**

#### 手順2: アダプタ名を控えておく

**内蔵ポートではないので、名前は「イーサネット」ではない。** `イーサネット 2` や `Ethernet 3` などになる。

```powershell
Get-NetAdapter | Where-Object { $_.InterfaceDescription -match "USB|Realtek|ASIX" } | Select-Object Name
```

**本手順書のコマンドに出てくる `name="イーサネット"` は、すべてこの実際の名前に置き換えること。** ここを間違えると 2.2 のIP設定も 2.3 のファイアウォール設定も別のアダプタに当たってしまい、原因が非常に分かりにくくなる。

#### 手順3: 実際に通信できるか

自宅のルータやスイッチに繋いで、IPが取れてpingが通ることを確認する。**これでドライバ・リンク・基本動作までまとめて検証できる。**

```powershell
ipconfig
ping 8.8.8.8
```

> マルチキャストの受信可否はG1が無いと確認できない。ここで確認できるのは「NICとして正常に動くか」まで。

#### 手順4: 省電力による切断を無効化する【必ずやる】

**USB接続のNICは、Windowsの省電力機能でリンクが落ちることがある。** 実際に広く報告されている問題で、1時間の実機セッション中にこれが起きるとパイプラインが止まる。

**デバイス個別の設定**

デバイスマネージャー → ネットワークアダプタ → 該当アダプタを右クリック → プロパティ → 電源の管理タブ
→ **「電力の節約のために、コンピューターでこのデバイスの電源をオフにできるようにする」のチェックを外す**

USBハブ経由の場合は、ユニバーサルシリアルバスコントローラー配下の **USB Root Hub** にも同じ設定があるので、そちらも外す。

**電源プラン側の設定**

```powershell
# USBのセレクティブサスペンドを無効化（現在の電源プランに対して）
powercfg /setacvalueindex SCHEME_CURRENT 2a737441-1930-4402-8d77-b2bebba308a3 48e6b7a6-50f5-4782-a5d4-53bb8f07e226 0
powercfg /setdcvalueindex SCHEME_CURRENT 2a737441-1930-4402-8d77-b2bebba308a3 48e6b7a6-50f5-4782-a5d4-53bb8f07e226 0
powercfg /setactive SCHEME_CURRENT
```

あわせて、**実機セッション中はPCをスリープさせない**設定にしておく（電源プランでスリープを「なし」に）。スリープからの復帰でUSBデバイスが再列挙され、リンクが落ちることがある。

#### 手順5: 接続の安定性

- **アダプタはPCへ直挿しする。** ハブを1段挟むほど障害点が増える
- **セッション中はアダプタを抜き差ししない。** USBポートを変えると別デバイスとして認識され、設定した静的IPが載らないことがある
- **予備を持っている意味**: 本命のアダプタで不審な挙動（リンクが落ちる、マルチキャストが届かない等）が出たとき、予備に差し替えて再現するかを見れば、アダプタ固有の問題かどうかを一発で切り分けられる。ただし**予備に替えたらアダプタ名が変わる**ので、2.2 のIP設定と 2.3 のファイアウォール設定をやり直すこと

#### 手順6: 【予備のドックを使う場合のみ】バスパワー動作時の電力に注意

> **本命のBENFEIアダプタには当てはまらない。** 単機能でハブを持たないため、電力を食い合う相手がいない。
> 以下は、予備のWAVLINKドックに切り替えた場合に読む。

ACアダプタを持たないバスパワー専用のドックは、**USBポートから供給される電力だけで全体を賄う**。ここが上限になる。

| ポート | 供給電力（規格上） |
|---|---|
| USB 3.0 / 3.2 Gen1 Type-A | 900mA @ 5V = **4.5W** |
| USB 2.0 Type-A | 500mA @ 5V = **2.5W** |

この中で、ドック内部のUSBハブコントローラと**Gigabit EthernetのPHY**が電力を食う。GbEのPHYは消費電力が大きい部類なので、USB 3.0の4.5Wなら収まるが**余裕は大きくない**。

守ること:

- **必ずUSB 3.0以上のポート（多くは青い端子）に挿す。** USB 2.0ポートだと2.5Wしかなく、電力不足でリンクが不安定になる、100Mbpsでしかリンクしない、そもそも認識されない、といった症状が出うる
- **セッション中はドックの他のポートを使わない。** 同じ4.5Wを食い合うので、USBメモリやスマホ充電を繋ぐとEthernetが不安定になる。**これが最も現実的なリスク**
- **ドック内部のハブにも省電力設定がある。** デバイスマネージャーの「ユニバーサルシリアルバスコントローラー」配下に `Generic USB Hub` として現れるので、手順4と同様に電源の管理タブでチェックを外す
- Windowsに「**USBポートの電力サージ**」という通知が出たら電力不足のサイン。別のポートに挿し替える

**保険**: 単機能のUSB-Ethernetドングル（ドックではないもの）を予備に持っていくと安心。ハブ機能がないぶん消費電力が小さく、電力起因のトラブルを切り分けられる。

#### 速度について

100BASE-TX（100Mbps）のアダプタでも問題ない。この用途の通信量は音声の往復で512kbps程度なので、帯域は全く問題にならない。

ケーブルもストレートでよい。G1側のポートはGigabitでAuto MDI-Xに対応しているため、ストレート／クロスのどちらでもリンクする。

## 2. STEP 0 — 物理接続とネットワーク設定

### 2.1 接続

1. G1の電源を入れ、起動を待つ
2. G1の**首の後ろにあるEthernetポート**とPCを、LANケーブルで直結する

> Wi-Fi経由は避ける。マイク音声はUDPマルチキャストで流れており、ルータを越えない可能性が高い。

### 2.2 PCのIPアドレスを設定する

Unitree公式ドキュメントはユーザPCに `192.168.123.99` を推奨している。

**GUIでやる場合**
設定 → ネットワークとインターネット → イーサネット → IP割り当て → 編集 → 手動 → IPv4オン

| 項目 | 値 |
|---|---|
| IPアドレス | `192.168.123.99` |
| サブネットマスク | `255.255.255.0` |
| ゲートウェイ | **空欄のまま**（インターネットはWi-Fi側から出るため） |

**PowerShell（管理者権限）でやる場合**

```powershell
# まずNIC名を確認
Get-NetAdapter | Format-Table Name, InterfaceDescription, Status, LinkSpeed

# 設定（"イーサネット" は上で確認した実際の名前に置き換える）
netsh interface ip set address name="イーサネット" static 192.168.123.99 255.255.255.0
```

> **USB-Ethernetアダプタを使う場合、名前は「イーサネット」ではない**（`イーサネット 2` など）。
> 本手順書に出てくる `name="イーサネット"` は**すべて実際の名前に読み替えること**。
> 別のアダプタに設定してしまうと、症状が「なぜか繋がらない」だけになり原因が掴みにくい。

| DNSサーバー | **空欄のまま**（これもWi-Fi側に任せる） |

確認:

```powershell
ipconfig
#   イーサネット アダプター に 192.168.123.99 が出ていること
```

### 2.2.1 有線＝G1／Wi-Fi＝インターネットの併用を確認する

**この2つは同時に使える。** 有線でG1と喋りながら、Wi-Fi経由でOpenAI APIを叩く構成になる。

仕組みは経路表の**最長プレフィックス一致**。Windowsは宛先に最も具体的に一致する経路を選ぶ。

```
192.168.123.0/24  → イーサネット（G1）      ← /24 は具体的
0.0.0.0/0         → Wi-Fi のゲートウェイ    ← /0 は最も曖昧
```

`192.168.123.164`（G1）宛は前者に一致して有線へ、`api.openai.com` 宛は前者に一致しないのでデフォルト経路＝Wi-Fiへ流れる。

**絶対に守ること: 有線側にデフォルトゲートウェイを設定しない。** 設定するとデフォルト経路が2本になり、インターフェースメトリックの勝敗次第でインターネット向けの通信までG1側に流れてしまう。G1はルータではないのでそこで行き止まりになり、「G1とは通信できるのにAPIだけ繋がらない」という切り分けにくい状態になる。**これがこの構成で最も多い失敗。**

確認方法:

```powershell
# デフォルト経路が1本だけで、Wi-Fi側を向いているか
Get-NetRoute -DestinationPrefix 0.0.0.0/0 | Format-Table ifIndex, NextHop, InterfaceAlias, RouteMetric

# 経路表全体を見る場合
route print -4
```

`InterfaceAlias` がWi-Fiのアダプタ名になっていればOK。イーサネットの行が出てきたら、有線側のゲートウェイ設定を消す。

両方が生きているかの最終確認:

```powershell
ping 192.168.123.164                          # G1（有線経由）
Test-NetConnection api.openai.com -Port 443   # クラウド（Wi-Fi経由）
#   TcpTestSucceeded : True になればOK
```

**もしインターネットに出られない場合**、Wi-Fiのメトリックを優先させる。Windowsは自動メトリックでリンク速度の速い方（＝有線）を優先しがちなので、稀にこれが必要になる。

```powershell
# 数値が大きいほど優先度が低い
Set-NetIPInterface -InterfaceAlias "イーサネット" -InterfaceMetric 100
```

> **名前解決がおかしい場合**: 有線側にDNSサーバーが設定されていると、Windowsがそちらにも問い合わせて遅延や失敗の原因になる。有線側のDNSは空欄にしておくこと。

### 2.3 Windowsファイアウォールの設定（詰まりやすい）

**Windowsファイアウォールは受信UDPをブロックする。** これを外さないとマイクのマルチキャストが届かず、原因が分からないまま時間を溶かす。

まずG1と繋いだネットワークを**プライベートネットワーク**にする。

> **なぜ必要か**: 2.2 でデフォルトゲートウェイを空欄にしたため、Windowsはこのアダプタを「識別されていないネットワーク」と判定し、**パブリックプロファイル**に入れることが多い。パブリックは受信をより厳しく制限するので、マイクのマルチキャストが弾かれる。ゲートウェイを空欄にするのは正しい設定なので、代わりにここでプロファイルを直す。

```powershell
# 管理者権限のPowerShell
Get-NetConnectionProfile
Set-NetConnectionProfile -InterfaceAlias "イーサネット" -NetworkCategory Private
```

その上でPythonの受信を許可する。

```powershell
# 管理者権限。python.exe のパスは where python で確認
New-NetFirewallRule -DisplayName "G1 Voice UDP" -Direction Inbound `
  -Program "C:\Path\To\python.exe" -Action Allow -Protocol UDP
```

> どうしても通らない場合、**切り分けのために一時的にプライベートネットワークのファイアウォールを無効化**して試す方法もある。原因の特定ができたら必ず元に戻すこと。

### 2.4 疎通確認

```powershell
ping 192.168.123.164     # G1の開発用コンピュータ(PC2)
ping 192.168.123.161     # オーディオ制御のMCU
```

**合格条件**: 少なくともどちらか一方から応答がある。

> **PC2のIP `192.168.123.164` は固定で変更できない**とドキュメントに明記されている。`192.168.123.161` はオーディオ制御のMCUで、別のデバイス。
> どちらにも応答がなければ `arp -a` で `192.168.123.x` に何がいるか探す。
>
> PC側のIPは `192.168.123.x`（x ≠ 164, 161）なら何でもよい。本手順書はUnitree公式が推奨する `.99` を使うが、`.200` を使っている例もある。

**うまくいかないとき**

| 症状 | 対処 |
|---|---|
| どちらもping不達 | ケーブルの接続、G1の起動完了、PCのIP設定を確認 |
| `ipconfig` にIPが出ない | ケーブル未接続か、NIC名を間違えている |
| 「宛先ホストに到達できません」 | サブネットマスクが `255.255.255.0` か確認 |

**撤退ライン**: 15分で疎通しなければ、ケーブル・アダプタの物理的な故障を疑って予備に交換する。

## 3. STEP 1 — マイク受信確認【最重要】

**このステップが今回いちばん重要。** ここが通らないと何も始まらない。逆にここさえ通れば、あとは既に動くことを確認済みのコードが動くだけ。

Unitree SDKを一切使わないので、Windowsでそのまま実行できる。

```powershell
python tools\check_mic.py --local-ip 192.168.123.99 --seconds 20
```

実行したら**G1に向かって普通に話しかける。**

### 期待される出力（成功時）

```
マルチキャスト 239.168.123.161:5555 を 192.168.123.99 で受信します
（声を出すとRMSが跳ね上がれば成功）

  RMS 0.0421 |################                        |   320,000バイト

--- 結果 ---
  パケット数    : 1,250
  受信バイト数  : 320,000
  音声長換算    : 10.00秒（16kHz mono 16bit想定）
  RMSの最大値   : 0.0421

[OK] マイク音声が届いています。
```

**合格条件**: 声を出したときにRMSのバーが伸び、`[OK]` が出ること。

### 音声を保存して耳で確認する

数値だけでは不安なので、録って聴く。

```powershell
python tools\check_mic.py --local-ip 192.168.123.99 --seconds 15 --save mic_test.wav
```

`mic_test.wav` を再生して、自分の声がちゃんと入っているか、ノイズがどの程度かを確認する。**このノイズレベルが後のVAD調整の基準になる**ので、聴いておく価値がある。

### トラブルシューティング

| 症状 | 原因の候補 | 対処 |
|---|---|---|
| `ソケットの準備に失敗しました: No such device` | `--local-ip` がPCの実IPと違う | `ipconfig` で確認して指定し直す |
| `[NG] パケットが1つも届いていません` | ファイアウォール | STEP 0.3 を再確認。一時的に無効化して切り分ける |
| 同上 | 別NICでjoinしている | `--local-ip` に有線側のIPを明示。Wi-Fiを一時的に切って切り分ける |
| 同上 | L2セグメントが違う | 有線直結になっているか確認。ハブ・ルータを挟んでいないか |
| **パケットは届くがRMSが常に0.0000** | **G1内蔵の音声アシスタントがマイクを占有** | 下記参照 |

### 「パケットは届くがRMSが0」だった場合

これは調査レポート3章に書いた**既知の課題**。G1内蔵の音声アシスタントがWake-up Conversation Modeでないと音声データがゼロ値で返る、というコミュニティ報告がある。

試すこと:

1. G1の内蔵音声アシスタントを**ウェイクワードで起動**してから、もう一度 `check_mic.py` を走らせる
2. 逆に、アプリから内蔵アシスタントを**無効化**してから試す
3. G1を再起動して、アシスタントが起動する前に試す

**撤退ライン**: 20分試して駄目なら、マイク入力は諦めて **STEP 4以降（スピーカー再生）だけを検証する**。その場合、STT入力はPCのマイクで代替する。

```powershell
# マイクだけPCに逃がす縮退構成
python -m pc_pipeline.main --source local-mic --sink g1-bridge
```

「PCに話しかけると、G1が喋って返す」形にはなるので、パイプラインが成立することは示せる。

## 5. STEP 3A — ブリッジ配置【SSH接続できた場合】

> **G1は共有機材。この手順はG1の環境を一切変更しない。**
> 追加インストールもsudoも設定変更も行わない。置くファイルは `/tmp` の1つだけで、再起動すれば消える。
> ブリッジは起動時に本体の音量を記録し、終了時に元へ戻すので、次に使う人に影響しない。

### 5.1 転送

**PC側の別のPowerShellウィンドウで**（SSHセッションは開いたまま）:

```powershell
cd unitree-g1-physical-ai\voice-conversation
scp g1_bridge\bridge_server.py unitree@192.168.123.164:/tmp/
```

> **`/tmp` に置く**のがポイント。ホームディレクトリに置くと共有アカウント（`unitree`）に残り続けるが、`/tmp` なら再起動で自動的に消える。

### 5.2 起動（インストール不要）

`bridge_server.py` は**Python標準ライブラリだけで動く**。外部依存は `unitree_sdk2py` のみで、これはG1に元から入っている。**`pip install` は不要。**

```bash
# NIC名を確認（192.168.123.x が付いているものを探す）
ip addr
```

> LeRobotのドキュメントでもG1の有線インターフェースは `eth0` として扱われているので、**そのままで通ることが多い**。違っていたら上の出力に合わせる。

セッションが切れてもブリッジが死なないよう、`nohup` でバックグラウンド起動する。

```bash
nohup python3 /tmp/bridge_server.py --iface eth0 --port 8765 > /tmp/bridge.log 2>&1 &

# ログを確認（Ctrl+C で見るのをやめてもブリッジは動き続ける）
tail -f /tmp/bridge.log
```

### 期待される出力

```
[bridge] 現在の音量を記録: 42（終了時に戻す）
[bridge] AudioClient初期化完了 (iface=eth0)
[bridge] tcp://0.0.0.0:8765 で待機中
[bridge] 停止する場合は Ctrl+C（音量は自動で元に戻ります）
```

`nohup` で起動しておけば、**Wi-Fiが切れてもPCがスリープしてもSSH窓を閉じてもブリッジは生き残る。** 再接続して `tail -f /tmp/bridge.log` で状況を見られる。

### 停止（撤収時に必ず実行）

```bash
pkill -INT -f bridge_server.py
```

`-INT` を付けること。**音量の復元は終了処理の中で行われる**ので、`kill -9` で強制終了すると音量が戻らない。停止後にログの末尾を見て確認する。

```bash
tail -3 /tmp/bridge.log
#   [bridge] 音量を 42 に戻した   ← これが出ていればOK
```

### トラブルシューティング

| 症状 | 対処 |
|---|---|
| `ModuleNotFoundError: unitree_sdk2py` | PC2にSDKが入っていない。`pip3 list \| grep unitree` で確認。無ければ STEP 3B へ |
| `AudioClient初期化` で止まる | `--iface` が違う。`ip addr` で確認し直す |
| `Address already in use` | 別のブリッジが残っている。`pkill -INT -f bridge_server.py` してから再起動 |
| `音量の取得に失敗` と出る | 復元されないだけで動作はする。撤収時に本体アプリで音量を確認する |

**撤退ライン**: 15分で起動できなければ STEP 3B へ。

## 9. STEP 6 — 調整と計測

ここからは時間が許す限り。

### 9.1 エコーの確認（本命構成の場合のみ）

**G1のスピーカーの音をG1のマイクが拾うループが起きないか**を確認する。対策は実装済みだが、音量次第で破綻する可能性がある。

1. 音量を上げていきながら会話する
2. G1が自分の発話に反応し始めたら、それが限界音量

破綻する場合の対処:

```powershell

$env:ECHO_COOLDOWN_SEC="0.8"
```

### 9.2 VADの調整

`mic_test.wav` で聴いたノイズレベルを踏まえて調整する。

```powershell
# 声を拾ってくれない → 閾値を下げる（既定0.008）
$env:VAD_SILENCE_THRESHOLD="0.004"

# ノイズで勝手に認識が走る → 閾値を上げる
$env:VAD_SILENCE_THRESHOLD="0.015"

# 話の途中で切られる → 無音判定を伸ばす（既定1.0秒）
$env:VAD_SILENCE_DURATION="1.5"
```

調整できたら自動トリガを試す。

```powershell
python -m pc_pipeline.main --source g1-multicast --sink g1-bridge --trigger vad
```

**G1のサーボ音がVADを誤爆させないか**を、G1を動かしながら確認できるとなお良い。

### 9.3 レイテンシの改善

`--stream` を付けると、LLMの応答を文単位でTTSに流して最初の一文から喋り始める。

```powershell
python -m pc_pipeline.main --source g1-multicast --sink g1-bridge --stream
```

出力に `最初の一文まで X.XX秒` が出るので、付けない場合と比較する。

### 9.4 GDL人格の注入

時間があれば、GDLのプロファイルを読ませて人格が乗るか試す。


## 付録：Wi-Fi接続について（今回は使わない）

**今回は有線接続のみで進める。** G1は共有機材なので、Wi-Fi有効化は行わない。

### なぜやらないか

G1のPC2にはWi-Fi（`wlan0`）があるが、**rfkillでブロックされている**。有効化するには次のような操作が要る。

```bash
# ← これらは全て「再起動しても残る」変更。共有機材では原則やらない
sudo rfkill unblock all
sudo nmcli radio wifi on
sudo nmcli device set wlan0 managed yes
sudo systemctl restart NetworkManager
sudo nmcli connection add type wifi ... psk "<パスワード>"
```

問題は3つ。

- **永続する** — rfkillの解除もNetworkManagerの接続プロファイルも再起動後に残る。次に使う人が「なぜか知らないネットワークに繋がっている」状態になる
- **認証情報が残る** — Wi-Fiのパスワードが機体に保存される
- **sudoでシステムサービスを再起動する** — 他の人の作業中だと影響が出る可能性がある

どうしても必要なら、**機材の管理者に確認してから**行い、使い終わったら元に戻すこと。

### 仮にWi-Fiを使う場合の技術的な整理

将来の参考として、通る／通らないの整理だけ残しておく。

| 経路 | 通信方式 | Wi-Fi | 理由 |
|---|---|---|---|
| スピーカー（ブリッジ） | TCPユニキャスト | 通る | IPで到達できればよい。帯域も256kbps程度で余裕 |
| マイク（マルチキャスト直接受信） | UDPマルチキャスト | 通らない見込み | 下記参照 |
| マイク（ブリッジ経由の中継） | TCPユニキャスト | 通る | スピーカーと同じ経路に乗る |

マイクのマルチキャストがWi-Fiで通らないと考える理由（**未検証の推測**）:

- あのマルチキャストはG1内部の**有線セグメント**（192.168.123.x）でRockChip系MCUが配信している。PC2の `wlan0` 側へブリッジやIGMPプロキシが設定されていない限り、Wi-Fi網には出てこない
- 仮に同一L2に見えたとしても、Wi-Fiのマルチキャストは最低基本レートで送られAP側でフィルタされることも多く、信頼できない

したがってWi-Fi運用時は `--source g1-bridge --sink g1-bridge`（マイクもスピーカーもブリッジ経由）になる。

なおLeRobotのドキュメントもWi-Fi接続を「experimental」とし、レイテンシの観点から有線を推奨している。**G1を歩かせながら会話させたい場合**以外に、Wi-Fiを選ぶ理由は薄い。

## 付録：wheelの正しい落とし方（バックアップ手順用）

**TCP版ブリッジを使う限りこの作業は不要。** WebSocket版（5-B）に切り替える場合だけ必要になる。

**素直に `pip download websockets` とやると失敗する。** 理由が2つある。

**理由1: CPUアーキテクチャが違う**

WindowsのPCは x86_64、G1のPC2（Jetson Orin NX）は **ARM64（aarch64）**。`pip download` は既定で「実行中のマシン向け」のwheelを取ってくるので、Windowsで叩くと `win_amd64` のwheelが落ちてきて、G1では絶対に入らない。websocketsはプラットフォーム別に147個のwheelを配布している。

**理由2: Pythonのバージョン要求が違う**

| websockets | 要求Python |
|---|---|
| 17.x | >= 3.11 |
| 16.x | >= 3.10 |
| 14.x 〜 15.x | >= 3.9 |
| 12.0 〜 13.1 | >= 3.8 |

G1のPC2がUbuntu 20.04ならPythonは3.8なので、**最新の17.xは入らない**。

**解決策: pure-Python wheel を、対象Pythonバージョンを指定して落とす**

websocketsはC拡張入りのwheelとは別に、**どのOS/CPUでも動く pure-Python wheel（`py3-none-any`）** も配布している。これを狙えばアーキテクチャの問題が消える。

```powershell
pip download websockets --no-deps --only-binary=:all: --platform any --python-version 3.8 --implementation py --abi none -d wheels
```

取得されるもの:

```
websockets-13.1-py3-none-any.whl
```

> **`--python-version 3.8` を指定する意味**: 3.8を指定すると「3.8以上で動く最新版」として13.1が選ばれる。13.1はPython 3.8でも3.12でも動くので、**G1のPythonが何であっても入る**。逆に指定を省くとPC側のPython（3.11等）向けに17.xが選ばれてしまい、G1が3.8だと入らない。

> **バージョン差は問題ない。** G1側 websockets 13.1 と PC側 17.1 の組み合わせで、ブリッジの往復通信が正常に動くことを検証済み。

## 付録：Mac（Apple Silicon）で動かす場合

**PC側のコードはOS非依存に作ってあるので、M1/M2以降のMacでもそのまま動く。** SDKを一切使わない設計にした恩恵で、`unitree_sdk2py` がApple Siliconで動くかどうかを気にする必要もない（依存するのはG1側のブリッジだけ）。

Windows機のバックアップとして持っていく価値は高い。当日Windows側で予期しない問題が出ても、同じコードをMacで動かせる。

### Windowsより楽な点

- **ssh / scp が最初から入っている** — OpenSSHクライアントの追加インストールが不要
- **ファイアウォールのプロファイル問題がない** — 「識別されていないネットワーク→パブリック」のような罠がない
- Pythonの依存（numpy / scipy / sounddevice / openai）はすべてarm64のwheelが用意されている

### 注意点1: USBポートの形状

M1 MacBookは**USB-C（Thunderbolt）のみ**。本命のBENFEIアダプタがUSB-A版なら、**USB-C変換アダプタかUSB-Cハブが別途必要**。当日忘れると詰むので、持ち物に加えること。

### 注意点2: IPアドレスの設定

システム設定 → ネットワーク → 該当アダプタ → 詳細 → TCP/IP → IPv4の構成:「手入力」

| 項目 | 値 |
|---|---|
| IPアドレス | `192.168.123.99` |
| サブネットマスク | `255.255.255.0` |
| ルーター | **空欄のまま**（インターネットはWi-Fi側から出るため） |

コマンドでやる場合:

```bash
# サービス名を確認（"USB 10/100/1000 LAN" のような名前）
networksetup -listallnetworkservices

networksetup -setmanual "USB 10/100/1000 LAN" 192.168.123.99 255.255.255.0
```

Windowsと同じく**ルーターを空欄にする**のが重要。macOSはルーターが未設定のサービスにはデフォルト経路を作らないので、インターネットはWi-Fi側から出る。確認は次の通り。

```bash
netstat -rn -f inet | head          # default が Wi-Fi (en0) を向いているか
route get 192.168.123.164           # interface が USBアダプタになっているか
ping 192.168.123.164
curl -sS -o /dev/null -w "%{http_code}\n" https://api.openai.com/v1/models
```

サービスの優先順位を見たい場合:

```bash
networksetup -listnetworkserviceorder
```

### 注意点3【重要】: ローカルネットワーク権限とマルチキャストの不具合

**macOSにはWindowsに無いリスクがある。**

macOSはローカルネットワークへのアクセスをアプリごとに許可制にしている。Terminal（またはiTerm、VS Code）からPythonを実行すると、初回に「"ターミナル"がローカルネットワーク上のデバイスの検出と接続を求めています」というダイアログが出る。**これを許可しないとマルチキャストが受信できない。**

さらに厄介なのが、**macOS 15 (Sequoia) 系および macOS 26.0〜26.4 に、権限を許可済みでも再起動後にマルチキャストが受信できなくなる不具合がある**こと。Appleの開発者フォーラムでDTSエンジニアが原因を説明していて、ローカルネットワーク権限の判定がIPCで行われる設計になっており、起動直後にそのIPCが失敗すると「安全側に倒して拒否」した結果がキャッシュされてしまう、というもの。**macOS 26.5 beta で修正済み**とされている。

症状は「権限は許可になっているのにマルチキャストだけ届かない」で、非常に切り分けにくい。

**対処法**

1. システム設定 → プライバシーとセキュリティ → ローカルネットワーク で、Terminal（使っているアプリ）の許可を**一度オフにしてからオンに戻す**
2. スクリプトを再起動する（ソケットを開き直す）

**それでも駄目なら、マルチキャストを使わない構成に逃げる**

これがこの設計の効いてくるところで、**マイクをブリッジ経由にすればマルチキャストを一切使わない**（TCPユニキャストのみ）。macOS固有の権限問題を丸ごと回避できる。

```bash
python -m pc_pipeline.main --source g1-bridge --sink g1-bridge
```

Macを使うなら、**最初からこの構成にしておくのが無難**かもしれない。切り分けの手間が減る。

### 注意点4: 事前確認

Windowsと同じく、前日にPCだけでパイプラインを通しておく。

```bash
python3 tests/test_pipeline_logic.py
python3 -m pc_pipeline.main --source local-mic --sink local-speaker
```

このとき**マイクへのアクセス許可**も求められるので、あわせて許可しておく（システム設定 → プライバシーとセキュリティ → マイク）。
