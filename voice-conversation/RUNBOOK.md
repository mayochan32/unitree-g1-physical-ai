# Unitree G1 音声会話 実機テスト 当日手順書

対象: PC = Windows / 構成B（G1ブリッジ型）
関連: `README.md`（概要）, `design-pc-pipeline.md`（設計）, `research-report.md`（調査）

---

## 0. この手順書の使い方

### 原則：下から順に潰す。飛ばさない。

いきなりパイプライン全体を動かそうとすると、失敗したときに原因の切り分けができなくなる。**STEP 1 → 2 → 3 → 4 → 5 の順に、各ステップの合格条件を満たしてから次へ進む。**

### 所要時間の目安

| STEP | 内容 | 目安 |
|---|---|---|
| 0 | 物理接続・ネットワーク設定 | 15分 |
| 1 | マイク受信確認 | 10分 |
| 2 | SSH可否の確認（ルート分岐） | 5分 |
| 3 | ブリッジ配置 or 縮退準備 | 15分 |
| 4 | スピーカー再生確認 | 10分 |
| 5 | パイプライン全体 | 15分 |
| 6 | 調整・計測 | 残り時間 |

**STEP 0〜4 で1時間**を見ておく。ここが通れば STEP 5 は事前に完成させてあるので設定切り替えだけで動く。

### 撤退ラインを決めておく

各ステップに「ここまでやって駄目なら次の手に移る」時間を書いてある。**限られた実機時間を1箇所で溶かさないこと。** 特にSSH接続とSDKのビルドは沼になりやすい。

## 1. 前日までの準備

### 1.1 持ち物チェックリスト

- [ ] Windows PC（充電済み・電源アダプタ）
- [ ] **有線LANケーブル**（G1との接続に必須）
- [ ] **USB-Ethernetアダプタ**（PCに有線ポートが無い場合。忘れると詰む）
- [ ] G1本体・バッテリー（充電済み。連続稼働は約2時間）
- [ ] G1の充電器
- [ ] テザリング用のスマホ（OpenAI APIにインターネット接続が必要）
- [ ] 静かな場所の確保（VADの閾値調整に効く）

### 1.2 PCの事前セットアップ（当日にやらない）

```powershell
# リポジトリを取得
git clone https://github.com/mayochan32/unitree-g1-physical-ai.git
cd unitree-g1-physical-ai\voice-conversation

# 依存をインストール
pip install -r requirements.txt

# APIキーを設定（PowerShell。永続化するなら setx を使う）
$env:OPENAI_API_KEY="sk-..."
```

### 1.3 事前に必ず通しておくこと（最重要）

**G1が無くても、PCだけでパイプライン全体を動かせる。** これを前日までに必ず成功させておく。

```powershell
# ロジックの単体テスト（APIキー不要）
python tests\test_pipeline_logic.py
#   → 13/13 件成功 と出れば OK

# PCのマイクとスピーカーで実際に会話してみる（APIキー必要）
python -m pc_pipeline.main --source local-mic --sink local-speaker
```

ここで会話が成立していれば、**当日残っている不確実性はG1との接続だけ**になる。逆にここを当日やろうとすると、APIキーの問題なのかネットワークの問題なのかG1の問題なのか分からなくなる。

### 1.4 インターネット接続の確保

OpenAI APIを叩くのでインターネットが要る。ただし**G1との通信は有線（192.168.123.x）**を使うので、次のどちらかになる。

- PCの有線＝G1、Wi-Fi＝インターネット（推奨。同時に使える）
- スマホのUSBテザリング＋有線＝G1

Wi-Fiとの併用時、Windowsが有線側をデフォルトゲートウェイにしてしまうとインターネットに出られなくなることがある。G1側のNICには**デフォルトゲートウェイを設定しない**こと（後述）。

## 2. STEP 0 — 物理接続とネットワーク設定

### 2.1 接続

1. G1の電源を入れ、起動を待つ
2. G1の**首の後ろにあるEthernetポート**とPCを、LANケーブルで直結する

> Wi-Fi経由は避ける。マイク音声はUDPマルチキャストで流れており、ルータを越えない可能性が高い。

### 2.2 PCのIPアドレスを設定する

Unitree公式ドキュメントはユーザPCに `192.168.123.99` を推奨している。

**GUIでやる場合**
設定 → ネットワークとインターネット → イーサネット → IP割り当て → 編集 → 手動 → IPv4オン

| 項目 | 値 |
|---|---|
| IPアドレス | `192.168.123.99` |
| サブネットマスク | `255.255.255.0` |
| ゲートウェイ | **空欄のまま**（インターネットはWi-Fi側から出るため） |

**PowerShell（管理者権限）でやる場合**

```powershell
# まずNIC名を確認
Get-NetAdapter

# 設定（"イーサネット" の部分は上で確認した名前に置き換える）
netsh interface ip set address name="イーサネット" static 192.168.123.99 255.255.255.0
```

確認:

```powershell
ipconfig
#   イーサネット アダプター に 192.168.123.99 が出ていること
```

### 2.3 Windowsファイアウォールの設定（詰まりやすい）

**Windowsファイアウォールは受信UDPをブロックする。** これを外さないとマイクのマルチキャストが届かず、原因が分からないまま時間を溶かす。

まずG1と繋いだネットワークを**プライベートネットワーク**にする。

```powershell
# 管理者権限のPowerShell
Get-NetConnectionProfile
Set-NetConnectionProfile -InterfaceAlias "イーサネット" -NetworkCategory Private
```

その上でPythonの受信を許可する。

```powershell
# 管理者権限。python.exe のパスは where python で確認
New-NetFirewallRule -DisplayName "G1 Voice UDP" -Direction Inbound `
  -Program "C:\Path\To\python.exe" -Action Allow -Protocol UDP
```

> どうしても通らない場合、**切り分けのために一時的にプライベートネットワークのファイアウォールを無効化**して試す方法もある。原因の特定ができたら必ず元に戻すこと。

### 2.4 疎通確認

```powershell
ping 192.168.123.164     # G1の開発用コンピュータ(PC2)
ping 192.168.123.161     # オーディオ制御のMCU
```

**合格条件**: 少なくともどちらか一方から応答がある。

> 情報源によってオンボードPCのIPが `192.168.123.164` とされているものと `192.168.123.161` とされているものがある。機体の構成によって異なる可能性があるので、両方試す。どちらも応答がなければ `arp -a` で `192.168.123.x` に何がいるか探す。

**うまくいかないとき**

| 症状 | 対処 |
|---|---|
| どちらもping不達 | ケーブルの接続、G1の起動完了、PCのIP設定を確認 |
| `ipconfig` にIPが出ない | ケーブル未接続か、NIC名を間違えている |
| 「宛先ホストに到達できません」 | サブネットマスクが `255.255.255.0` か確認 |

**撤退ライン**: 15分で疎通しなければ、ケーブル・アダプタの物理的な故障を疑って予備に交換する。

## 3. STEP 1 — マイク受信確認【最重要】

**このステップが今回いちばん重要。** ここが通らないと何も始まらない。逆にここさえ通れば、あとは既に動くことを確認済みのコードが動くだけ。

Unitree SDKを一切使わないので、Windowsでそのまま実行できる。

```powershell
python tools\check_mic.py --local-ip 192.168.123.99 --seconds 20
```

実行したら**G1に向かって普通に話しかける。**

### 期待される出力（成功時）

```
マルチキャスト 239.168.123.161:5555 を 192.168.123.99 で受信します
（声を出すとRMSが跳ね上がれば成功）

  RMS 0.0421 |################                        |   320,000バイト

--- 結果 ---
  パケット数    : 1,250
  受信バイト数  : 320,000
  音声長換算    : 10.00秒（16kHz mono 16bit想定）
  RMSの最大値   : 0.0421

[OK] マイク音声が届いています。
```

**合格条件**: 声を出したときにRMSのバーが伸び、`[OK]` が出ること。

### 音声を保存して耳で確認する

数値だけでは不安なので、録って聴く。

```powershell
python tools\check_mic.py --local-ip 192.168.123.99 --seconds 15 --save mic_test.wav
```

`mic_test.wav` を再生して、自分の声がちゃんと入っているか、ノイズがどの程度かを確認する。**このノイズレベルが後のVAD調整の基準になる**ので、聴いておく価値がある。

### トラブルシューティング

| 症状 | 原因の候補 | 対処 |
|---|---|---|
| `ソケットの準備に失敗しました: No such device` | `--local-ip` がPCの実IPと違う | `ipconfig` で確認して指定し直す |
| `[NG] パケットが1つも届いていません` | ファイアウォール | STEP 0.3 を再確認。一時的に無効化して切り分ける |
| 同上 | 別NICでjoinしている | `--local-ip` に有線側のIPを明示。Wi-Fiを一時的に切って切り分ける |
| 同上 | L2セグメントが違う | 有線直結になっているか確認。ハブ・ルータを挟んでいないか |
| **パケットは届くがRMSが常に0.0000** | **G1内蔵の音声アシスタントがマイクを占有** | 下記参照 |

### 「パケットは届くがRMSが0」だった場合

これは調査レポート3章に書いた**既知の課題**。G1内蔵の音声アシスタントがWake-up Conversation Modeでないと音声データがゼロ値で返る、というコミュニティ報告がある。

試すこと:

1. G1の内蔵音声アシスタントを**ウェイクワードで起動**してから、もう一度 `check_mic.py` を走らせる
2. 逆に、アプリから内蔵アシスタントを**無効化**してから試す
3. G1を再起動して、アシスタントが起動する前に試す

**撤退ライン**: 20分試して駄目なら、マイク入力は諦めて **STEP 4以降（スピーカー再生）だけを検証する**。その場合、STT入力はPCのマイクで代替する。

```powershell
# マイクだけPCに逃がす縮退構成
python -m pc_pipeline.main --source local-mic --sink g1-bridge
```

「PCに話しかけると、G1が喋って返す」形にはなるので、パイプラインが成立することは示せる。

## 4. STEP 2 — SSH可否の確認（ルート分岐点）

ここで本命ルートか縮退ルートかが決まる。

```powershell
ssh unitree@192.168.123.164
# パスワード: 123
```

`192.168.123.164` で繋がらなければ `192.168.123.161` も試す。

> 認証情報 `unitree` / `123` はサードパーティのドキュメントに記載されていたもの。**機体によって変更されている可能性がある**ので、繋がらなければ機体の付属資料を確認する。

### 接続できたら → STEP 3A（本命ルート）
### 接続できなければ → STEP 3B（縮退ルート）

**撤退ライン**: 10分で繋がらなければ迷わず STEP 3B に移る。ここで粘っても得るものは少ない。

## 5. STEP 3A — ブリッジ配置【SSH接続できた場合】

### 5.1 転送

**PC側の別のPowerShellウィンドウで**（SSHセッションは開いたまま）:

```powershell
cd unitree-g1-physical-ai\voice-conversation
scp g1_bridge\bridge_server.py unitree@192.168.123.164:~/
```

### 5.2 G1側で起動

SSHセッションの中で:

```bash
# websocketsが入っていなければ入れる
pip3 install websockets

# NIC名を確認（192.168.123.x が付いているものを探す）
ip addr

# 起動（eth0 の部分は上で確認した名前に）
python3 bridge_server.py --iface eth0 --port 8765
```

### 期待される出力

```
[bridge] AudioClient初期化完了 (iface=eth0)
[bridge] ws://0.0.0.0:8765 で待機中
```

**このSSHセッションは開いたままにしておく。** ブリッジはここで動き続ける。

### トラブルシューティング

| 症状 | 対処 |
|---|---|
| `ModuleNotFoundError: unitree_sdk2py` | PC2にSDKが入っていない。`pip3 list \| grep unitree` で確認。無ければ STEP 3B へ |
| `pip3 install websockets` がネットワークエラー | G1がインターネットに出られない。PCで `pip download websockets` して `scp` で持ち込む |
| `AudioClient初期化` で止まる | `--iface` が違う。`ip addr` で確認し直す |

**撤退ライン**: 15分で起動できなければ STEP 3B へ。

## 6. STEP 3B — 縮退ルート【SSH接続できない場合】

ブリッジが置けないので、**音はPCのスピーカーから出す**。マイクはG1のものを使えるので、パイプラインが動くことは示せる。

準備は不要。STEP 4 を飛ばして STEP 5 に進み、次のコマンドを使う。

```powershell
python -m pc_pipeline.main --source g1-multicast --sink local-speaker
```

> この構成では**エコー問題が起きない**（G1のマイクとPCのスピーカーが離れているため）ので、かえって安定して動く。VADやSTT精度の検証にはむしろ好都合。

---

## 7. STEP 4 — スピーカー再生確認【STEP 3Aを通った場合】

PC側から、SDKを使わずにブリッジ経由で音を鳴らす。

```powershell
python tools\check_bridge.py --host 192.168.123.164
```

### 期待される出力（成功時）

```
接続先: ws://192.168.123.164:8765
再生時間: 1.00秒 (32,000バイト)
接続しました。PCMを送ります…
送信完了。playback_done を待ちます…

[OK] playback_done を受信（往復 1.00秒）
G1から音が聞こえましたか？
```

**合格条件**: G1から440Hzのトーンが1秒鳴り、`playback_done` が返ること。

> 往復時間が音声長（1.00秒）とほぼ一致するのが正常。ここが大幅に短いと「送信完了で返している」ことになり、エコー対策の同期が壊れる。

### 音量調整

聞こえにくければブリッジ側のログを見つつ、パイプライン起動後に調整する。音量はG1本体のアプリからも変えられる。

### トラブルシューティング

| 症状 | 対処 |
|---|---|
| `接続に失敗しました` | ブリッジが起動しているか、SSHセッションのログを確認 |
| 同上 | PCのファイアウォールが送信TCPを塞いでいないか |
| `playback_done` が返らない | ブリッジ側のログにエラーが出ていないか確認 |
| 接続はできるが音が出ない | G1の音量がゼロでないか。本体スピーカーの物理的な確認 |

## 8. STEP 5 — パイプライン全体

いよいよ会話させる。**まずプッシュトゥトーク（既定）で試す。**

```powershell
# 本命構成
python -m pc_pipeline.main --source g1-multicast --sink g1-bridge

# 縮退構成（STEP 3Bの場合）
python -m pc_pipeline.main --source g1-multicast --sink local-speaker
```

### 操作方法

1. `[Enter]で話しかける` と出たら Enter を押す
2. `LISTENING（話してください）` と出たらG1に話しかける
3. 話し終えて1秒黙ると自動で認識に進む
4. G1が音声で返答する
5. `q` + Enter で終了

### 期待される出力

```
============================================================
  入力: g1-multicast
  出力: g1-bridge
  STT : gpt-4o-transcribe
  LLM : gpt-4o-mini
  TTS : gpt-4o-mini-tts / voice=alloy
============================================================
  [情報] トリガ方式: ptt

[Enter]で話しかける / 'q'+[Enter]で終了 >
  ... LISTENING（話してください）
  ... THINKING
あなた: こんにちは、調子はどうですか  （STT 0.82秒）
G1    : こんにちは。問題なく動いていますよ。  （LLM 1.15秒）
  [計測] 発話終了から応答完了まで 4.21秒
```

**合格条件**: 話しかけた内容が正しく認識され、G1が音声で返答すること。

### トラブルシューティング

| 症状 | 対処 |
|---|---|
| `OPENAI_API_KEY が設定されていません` | `$env:OPENAI_API_KEY="sk-..."` を実行 |
| `音声が届きません` | STEP 1 に戻る |
| 認識結果が空 | 声が小さいか、VAD閾値が高すぎる。STEP 6 参照 |
| すぐに認識が終わってしまう | VAD閾値が低すぎてノイズを声と誤判定。STEP 6 参照 |
| OpenAI APIのタイムアウト | インターネット接続を確認。Wi-Fi側が生きているか |

## 9. STEP 6 — 調整と計測

ここからは時間が許す限り。

### 9.1 エコーの確認（本命構成の場合のみ）

**G1のスピーカーの音をG1のマイクが拾うループが起きないか**を確認する。対策は実装済みだが、音量次第で破綻する可能性がある。

1. 音量を上げていきながら会話する
2. G1が自分の発話に反応し始めたら、それが限界音量

破綻する場合の対処:

```powershell
# 再生後にマイクを捨てる時間を伸ばす（既定0.4秒）
$env:ECHO_COOLDOWN_SEC="0.8"
```

### 9.2 VADの調整

`mic_test.wav` で聴いたノイズレベルを踏まえて調整する。

```powershell
# 声を拾ってくれない → 閾値を下げる（既定0.008）
$env:VAD_SILENCE_THRESHOLD="0.004"

# ノイズで勝手に認識が走る → 閾値を上げる
$env:VAD_SILENCE_THRESHOLD="0.015"

# 話の途中で切られる → 無音判定を伸ばす（既定1.0秒）
$env:VAD_SILENCE_DURATION="1.5"
```

調整できたら自動トリガを試す。

```powershell
python -m pc_pipeline.main --source g1-multicast --sink g1-bridge --trigger vad
```

**G1のサーボ音がVADを誤爆させないか**を、G1を動かしながら確認できるとなお良い。

### 9.3 レイテンシの改善

`--stream` を付けると、LLMの応答を文単位でTTSに流して最初の一文から喋り始める。

```powershell
python -m pc_pipeline.main --source g1-multicast --sink g1-bridge --stream
```

出力に `最初の一文まで X.XX秒` が出るので、付けない場合と比較する。

### 9.4 GDL人格の注入

時間があれば、GDLのプロファイルを読ませて人格が乗るか試す。

```powershell
python -m pc_pipeline.main --source g1-multicast --sink g1-bridge --gdl-profile path\to\profile.json
```

## 11. トラブルシューティング早見表

| 困っていること | 最初に見るところ |
|---|---|
| G1にpingが通らない | PCのIP設定（`ipconfig`）、ケーブル |
| マイクのパケットが届かない | **Windowsファイアウォール**、`--local-ip` の指定 |
| パケットは届くがRMSが0 | G1内蔵音声アシスタントとの競合（既知課題） |
| SSHできない | IPを両方試す（.164 と .161）。10分で諦めて縮退ルートへ |
| ブリッジが起動しない | PC2にSDKが入っているか、`--iface` が合っているか |
| ブリッジに繋がらない | ブリッジのログ、PCのファイアウォール（送信TCP） |
| 音が出ない | G1本体の音量 |
| G1が自分の声に反応する | `ECHO_COOLDOWN_SEC` を伸ばす、音量を下げる |
| 認識が始まらない/勝手に始まる | `VAD_SILENCE_THRESHOLD` を調整 |
| APIがタイムアウト | インターネット接続（Wi-Fi側） |

## 付録：Wi-Fi接続で運用する

有線を引き回したくない場合、Wi-Fiでも動かせる。ただし**マイクとスピーカーで事情が違う**ので、構成が変わる。

### 何がWi-Fiで通って、何が通らないか

| 経路 | 通信方式 | Wi-Fi | 理由 |
|---|---|---|---|
| スピーカー（ブリッジ） | WebSocket = TCPユニキャスト | **通る** | IPで到達できればよい。帯域も256kbps程度で余裕 |
| マイク（マルチキャスト直接受信） | UDPマルチキャスト | **通らない見込み** | 下記参照 |
| マイク（ブリッジ経由の中継） | WebSocket = TCPユニキャスト | **通る** | スピーカーと同じ経路に乗る |

マイクのマルチキャストがWi-Fiで通らないと考える理由（**未検証の推測**）:

- あのマルチキャストはG1内部の**有線セグメント**（192.168.123.x）でRockChip系MCUが配信している。PC2の `wlan0` 側へブリッジやIGMPプロキシが設定されていない限り、Wi-Fi網には出てこない
- 仮に同一L2に見えたとしても、Wi-Fiのマルチキャストは最低基本レートで送られAP側でフィルタされることも多く、信頼できない

当日 `check_mic.py` をWi-Fi接続で走らせれば実際に確かめられる。届けば儲けもの、というくらいの期待値で。

### 前提：G1のWi-Fiはデフォルトで無効

G1のPC2にはWi-Fi（`wlan0`）があるが、**rfkillでブロックされている**。解除には有線でSSHする必要があるので、**最初の1回は必ず有線接続が要る**。

```bash
# 有線でSSHしてから実行
ssh unitree@192.168.123.164     # パスワード: 123

sudo rfkill unblock all
sudo ip link set wlan0 up
sudo nmcli radio wifi on
sudo nmcli device set wlan0 managed yes
sudo systemctl restart NetworkManager

# 接続可能なAPを探して繋ぐ
nmcli device wifi list
sudo nmcli device wifi connect "<SSID>" password "<パスワード>"

# 割り当てられたIPを確認（このIPを後で使う）
ip addr show wlan0
```

> Unitree/lerobotのドキュメントはWi-Fi SSHを「experimental」と位置づけ、ネットワーク由来のレイテンシに注意するよう書いている。

### Wi-Fi運用時の構成

**マイクもスピーカーもブリッジ経由**にする。これで完全ワイヤレスになる。

```powershell
# ブリッジのホストをWi-Fi側のIPに向ける
$env:G1_BRIDGE_HOST="<wlan0のIP>"

python -m pc_pipeline.main --source g1-bridge --sink g1-bridge
```

ブリッジ側は有線のときと同じで構わない（待ち受けは `0.0.0.0` なので両方のNICで受ける）。

```bash
python3 bridge_server.py --iface eth0 --port 8765
```

`--iface` は**DDS通信に使うNIC**の指定なので、G1内部の有線NIC（`eth0`）のままにしておくこと。ここをwlan0にすると、G1内部のスピーカー制御に到達できなくなる。

### 動作確認

```powershell
python tools\check_bridge.py --host <wlan0のIP>
```

### Wi-Fi運用の注意点

- **遅延とジッタが乗る。** 帯域（往復512kbps程度）は足りているが、パケットロス→TCP再送のたびに音が途切れる可能性がある
- **応答レイテンシの計測には向かない。** 計測やデモは有線で行う方が結果が安定する
- **APを挟むので経路が長い。** G1とPCが同じAPに繋がっていても、通信はAP経由になる

### 使い分けの目安

| 目的 | 推奨 |
|---|---|
| 初回の立ち上げ・切り分け | **有線**（不確実性を減らす） |
| レイテンシ計測・デモ | **有線** |
| G1を歩かせながら会話させる | **Wi-Fi**（有線では物理的に無理） |
| 取り回し重視の試行錯誤 | Wi-Fi |
